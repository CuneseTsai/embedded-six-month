# 学习日志规范

## 1. 目的

学习日志用于记录实际发生的学习、实验、调试和验证过程，为复习、项目开发和后续会话恢复提供可靠依据。

日志必须反映真实执行结果。计划做的事情不能写成已完成，推测不能写成验证结论，阅读过的内容不能自动认定为掌握。

## 2. 文件命名

使用日期和主题命名：

`YYYY-MM-DD-topic.md`

示例：

- `2026-10-11-c-memory-layout.md`
- `2026-10-12-c-pointer-experiment.md`

同一天存在多个相互独立的主题时，可以在主题部分进一步区分。

## 3. 推荐模板

每篇日志根据实际需要采用以下结构。未涉及的章节可以删除，不要为了填满模板而编造内容。

```markdown
# 主题名称

日期：YYYY-MM-DD
关联路径：
关联分支：

## 一、学习目标

说明本次要回答的问题，以及完成标准。

## 二、开始前的状态

记录已有认识、前置条件、工具版本和相关代码状态。

## 三、实际操作

记录实际执行的命令、修改的代码、实验步骤和必要的环境信息。

## 四、观察结果与证据

记录真实输出、关键现象、汇编差异、测试结果或错误信息。
重要结论应尽可能附上可复现的证据。

## 五、原理分析

解释观察结果为什么出现，区分已经验证的结论与暂时的推断。

## 六、验证情况

逐项记录验证方法、预期结果、实际结果和结论。

## 七、知识状态

- 知道：
- 理解：
- 熟悉：
- 掌握（必须有明确验证依据）：

未验证的项目应标为待验证，不得仅凭阅读或照抄示例认定为掌握。

## 八、遗留问题与风险

记录尚未解释的现象、错误、边界条件和需要补充的实验。

## 九、本次结论

总结本次真正完成的工作及其适用范围。

## 十、下一步

写出可以直接执行的下一项任务，以及必要的文件路径或验证起点。
```

## 4. 记录规则

1. 只记录实际发生的操作和结果；无法确认的内容明确标注“待验证”。
2. 重要实验尽量保留最小可复现代码、编译参数、关键输出和环境信息。
3. 代码修改应与实验目的对应，避免一次改变多个变量而无法判断原因。
4. 区分“代码能够运行”“实验结果符合预期”和“能够独立解释并迁移应用”。
5. 对编译器优化、内存布局、并发、时序等主题，说明结论适用的编译选项、平台或实验条件。
6. 日志记录事实和技术判断；长期设计决策应同时写入工程决策记录。
7. 每次阶段结束时更新学习状态和下一次交接记录，避免日志与当前进度脱节。
8. 日志中可以保留必要的英文技术术语，解释性内容优先使用中文。

## 5. 学习状态判定原则

- 知道：能识别术语并说明其基本用途。
- 理解：能解释核心机制和主要因果关系。
- 熟悉：能在常见场景中独立使用，并处理典型问题。
- 掌握：能独立实现、解释关键细节、验证边界条件，并能分析常见故障。

状态必须依据实际表现动态调整。曾经学过、看懂答案或成功运行一次示例，都不足以单独证明已经掌握。
